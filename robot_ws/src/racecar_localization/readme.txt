	对这次大作业感触很深。
	一开始我们小组借助AI进行了科学的分工，鉴于我想加入的子系统是雷达，以后可能会遇到多传感器协同的工作，我选择了位姿数据融合的部分（虽然后面发现需要融合的传感器数据不包括雷达和相机
	在拿到仿真队友的模型前，我在B站上把赵虚左老师的话题通信巩固了一遍（python版），然后大概了解坐标变换的知识，后面发现其实这部分只要会用命令就差不多了。
	拿到模型后，在AI的指导下我开始搭建工具包，把launch和ekf.yaml文件写好准备尝试融合，不出意外地，意外发生了，融合命令根本没有输出，这时候我怀疑是传感器数据没输出，但查了一遍除了gps都有输出，问AI怎么办，它让我先关了gps，先把odom和imu的数据融了，我照做了还是不行，然后AI又一堆地怀疑时间戳和数据帧id有问题，就这样折腾了两天半，结合tf tree和一堆查传感器频率、状态的命令才定位出来仿真的文件里一些传感器所定义的frame_id对不齐，以及bridge文件里缺少了clock模块，然后仿真队友修改帧名、我加了clock后果不其然传感器数据能被正常融合、ros时钟和仿真时间对齐了，融合后节点能出数据了，我欣喜若狂，终于敲开了融合的大门，那一天晚上，我激动得不得了。
	第二天，大概是16号吧，我在rviz里引入两个基于融合前后里程计坐标系的odometry来可视化融合的好坏，在小车直线行走时，两个箭头的指向是能较好的重叠的，但在转弯后，两个坐标系的指向就会出现偏移，随着仿真时间的增加和小车的移动，二者差距会越来越大，问了AI很多次，它给出的答案是二者本来存在固定微小角度差、imu太敏感ekf太信任它给出的数据等等。逐个排查耗费了不少精力和耐心，但发现怎么改参数都实现不了较好的融合，（AI也提示过我把imu关了只用odom来融，但我觉得传感器数据融合就是要用多种数据才配叫融合，所以我最后还是采用了imu的数据）于是乎，鉴于进度的紧急，我只能硬着头皮把gps加进来了，结果吓我一跳融合后坐标系往小车的左边走，在AI的建议下我把gps所在的坐标系加了一个90°的偏向以对齐未融合前的odom坐标系，虽然解决了直行的融合效果，但转弯效果还是不太好。
	从6月11日小组正式分工到6月18日这一天，我的任务才算勉强落幕，为了让后面两名队友的任务能收工，我的融合就算有再多问题我也只能传到他们的工程里了，这8天，有数据融合不出来的苦恼和不解，有数据融合不理想的郁闷，也有反复的自我怀疑，怀疑自己是不是进车队的料，我迷茫了，但也许是释怀了，中间无数次有过想放弃的念头，想着摆烂，但想到我们是一个团队，大家都还等着我的数据融合，我还是咬咬牙坚持下来，明天都投入大量的时间解决报错和调参，做出了一个垃圾。
	也许我的实力还是不够，还得沉淀沉淀，就算最后没能如愿进队，我也很感谢车队给过我们的机会。
